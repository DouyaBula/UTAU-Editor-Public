# 原版 osu!lazer 编辑器导出行为分析

> 历史行为调查。现行文档统一由 [docs/README](../docs/README.md)索引；后续上游同步涉及的导出行为仍需按对应版本源码核对。本轮统一交互优化没有改动默认兼容导出器。

## 1. 文档目的

本文记录 osu!lazer 原版编辑器中 `File -> Export -> For compatibility (.osz)` 的导出流程，以及该流程可能对 `.osu` 谱面内容产生的修改。

本次调查最初用于确认以下现象：

> 在编辑器中允许物件位于游戏场边界外后，导出的 `.osz` 是否会把这些物件强制移动回 `0-512 x 0-384` 的标准游戏场范围。

最终结论是：

- osu!lazer 的兼容导出流程没有把普通 osu! 圆圈或滑条头坐标钳制到游戏场内。
- 出界坐标会被四舍五入为整数，但仍然保持为出界坐标。
- Spinner 是例外：legacy 解码时会将其位置固定为游戏场中心 `(256, 192)`。
- 实际观察到的场外物件归位或不可正常使用，更可能来自 osu!stable 的载入、编辑或保存行为，而不是 lazer 的 `.osz` 导出器。

因此当前不需要修改 lazer 的导出代码。

## 2. 导出入口

编辑器菜单入口位于：

```text
osu.Game/Screens/Edit/Editor.cs
```

`For compatibility (.osz)` 调用：

```csharp
manager.ExportLegacy(Beatmap.Value.BeatmapSetInfo)
```

实际执行链路为：

```text
Editor
  -> BeatmapManager.ExportLegacy()
  -> LegacyBeatmapExporter.ExportAsync()
  -> LegacyArchiveExporter.ExportToStream()
  -> LegacyBeatmapExporter.GetFileContents()
```

主要代码文件：

| 文件 | 职责 |
|---|---|
| `osu.Game/Screens/Edit/Editor.cs` | 编辑器导出菜单入口 |
| `osu.Game/Beatmaps/BeatmapManager.cs` | 管理 exporter 实例并发起导出 |
| `osu.Game/Database/LegacyArchiveExporter.cs` | 创建 `.osz` ZIP 归档并复制资源 |
| `osu.Game/Database/LegacyBeatmapExporter.cs` | 解码、兼容转换并重新编码 `.osu` 文件 |
| `osu.Game/Beatmaps/Formats/LegacyBeatmapDecoder.cs` | 将 `.osu` 文本解析为 beatmap 对象 |
| `osu.Game/Rulesets/Objects/Legacy/ConvertHitObjectParser.cs` | 解析 legacy hit object 与滑条路径 |
| `osu.Game/Beatmaps/WorkingBeatmap.cs` | 创建 ruleset 对应的 playable beatmap |
| `osu.Game.Rulesets.Osu/Beatmaps/OsuBeatmapConverter.cs` | 转换为 osu! ruleset 物件 |
| `osu.Game/Beatmaps/Formats/LegacyBeatmapEncoder.cs` | 将转换后的 beatmap 重新写成 `.osu` |

## 3. 导出流程概览

对于音频、图片、视频和其他普通资源，导出器基本直接复制原始文件。

对于每个 `.osu` 文件，流程不是直接复制，而是：

1. 从 lazer 文件存储读取已保存的 `.osu`。
2. 使用 `LegacyBeatmapDecoder` 解析文件。
3. 使用 `GetPlayableBeatmap()` 转换为对应 ruleset 的 playable beatmap。
4. 执行 ruleset beatmap processor 和 hit object 默认值计算。
5. 调用 `LegacyBeatmapExporter.MutateBeatmap()` 执行 stable 兼容转换。
6. 使用 `LegacyBeatmapEncoder` 重新生成整个 `.osu` 文件。
7. 将重新生成的 `.osu` 与其他资源一起写入 `.osz`。

因此，兼容导出的 `.osu` 通常不会与 lazer 内部保存的 `.osu` 保持字节一致。

## 4. `MutateBeatmap()` 的明确修改

以下修改直接写在：

```text
osu.Game/Database/LegacyBeatmapExporter.cs
```

### A1. 网格尺寸映射

`GridSize` 被映射为 stable 已知的值：

| 原值范围 | 导出值 |
|---|---:|
| `>= 24` | `32` |
| `>= 12` | `16` |
| `>= 6` | `8` |
| `< 6` | `4` |

影响：

- 自定义网格大小无法原样保留。
- 只影响编辑器网格设置，不改变物件位置。
- 如果未来需要降低转换强度，此项通常可以独立取消。

### A2. 红线时间向下取整

每个 timing point 的时间使用：

```csharp
Math.Floor(timingPoint.Time)
```

例如：

```text
284.725 -> 284
```

### A3. 红线区间内的控制点和物件整体偏移

红线向下取整时，导出器会计算：

```text
offset = floor(红线时间) - 原红线时间
```

同一 timing section 内：

- 所有控制点增加该 offset。
- 所有 hit object 的开始时间增加该 offset。

目的：

- 红线取整后仍维持物件相对于红线的节拍位置。

结果：

- 物件时间不是简单单独取整。
- 一个红线区间内的所有物件可能先整体平移，再进行后续取整。

### A4. 所有控制点时间向下取整

红线区间平移完成后，所有控制点再次执行：

```csharp
controlPoint.Time = Math.Floor(controlPoint.Time);
```

受影响的内容包括：

- Timing control points
- Difficulty control points
- Sample control points
- Effect control points

### A5. Break 时间向下取整

所有休息段的开始和结束时间都使用 `Math.Floor()`。

### A6. Hit object 开始时间向下取整

所有物件的 `StartTime` 都使用 `Math.Floor()`。

### A7. 非滑条持续时间物件的结束时间取整

对于实现 `IHasDuration`、但不实现 `IHasPath` 的物件：

- 先分别向下取整开始和结束时间。
- 再根据二者计算 Duration。

主要影响：

- Spinner
- osu!mania hold note

### A8. Hit object 头坐标四舍五入

实现 `IHasXPosition` / `IHasYPosition` 的物件会执行：

```csharp
X = MathF.Round(X);
Y = MathF.Round(Y);
```

重要结论：

- 这里只做整数四舍五入。
- 没有执行 `Math.Clamp()`。
- 没有限制到 `X = 0-512` 或 `Y = 0-384`。

例如：

```text
X = -50.4 -> -50
X = 600.7 -> 601
Y = -20.8 -> -21
```

这些结果仍然位于游戏场外。

### A9. 滑条控制点坐标四舍五入

滑条的相对控制点坐标也会四舍五入为整数。

结果：

- 滑条路径可能发生很小的形状变化。
- 场外控制点不会因为此步骤被移动回游戏场。

### A10. 清除最后一个控制点的曲线类型

当滑条至少包含两个控制点时，最后一个控制点的 `Type` 会被设为 `null`。

原因：

- stable 将滑条的最后一个非空类型错误地解释为整条滑条的曲线类型。
- 保留该类型可能导致 stable 中的滑条形状被破坏。

此项属于重要兼容处理，不建议独立取消。

### A11. 多段路径和 lazer 曲线转换为 Bezier

当路径不能直接由 stable 正确表示时：

- 使用 `BezierConverter.ConvertToModernBezier()` 转换。
- 清空原控制点。
- 使用转换后的 Bezier 控制点重建路径。

常见对象：

- 包含多种曲线类型的滑条。
- 多段路径。
- B-spline 或 stable 无法直接理解的路径表示。

### A12. Bezier 分段点重复

stable 使用重复控制点表示 Bezier 分段。

转换器会在每个新 Bezier segment 的开始位置额外写入一次相同控制点。

此项与 A11 配套，不能在保留 A11 的同时随意取消。

## 5. 解码阶段的隐式修改

兼容导出会先用 `LegacyBeatmapDecoder` 重新读取 `.osu`。解析过程本身就会规范化部分数据。

### B1. 难度值限制

解析结束后执行：

| 参数 | 限制范围 |
|---|---|
| HP Drain Rate | `0-10` |
| Circle Size，非 mania | `0-10` |
| Circle Size，mania | `1-MAX_MANIA_KEY_COUNT` |
| Overall Difficulty | `0-10` |
| Approach Rate | `0-10` |
| Slider Multiplier | `0.4-3.6` |
| Slider Tick Rate | `0.5-8` |

如果内部谱面允许超出这些范围，兼容导出会丢失超范围值。

### B2. 编辑器参数限制

解析 `[Editor]` 时：

- `DistanceSpacing` 最低为 0。
- `TimelineZoom` 最低为 0。
- `BeatDivisor` 被限制到框架定义的最小和最大 divisor。

### B3. Hit object 按开始时间排序

解析完成后：

```csharp
HitObjects = HitObjects.OrderBy(h => h.StartTime).ToList();
```

相同时间的物件保持稳定排序，但手工构造的非时间顺序会被修正。

### B4. Break 结束时间修复

Break 的结束时间使用：

```csharp
end = Math.Max(start, parsedEnd);
```

结束时间早于开始时间的非法 break 会被修复。

### B5. Spinner 坐标强制归位

`ConvertHitObjectParser` 在解析 spinner 时，不使用文件中的 X/Y，而是创建：

```csharp
new Vector2(512, 384) / 2
```

也就是：

```text
(256, 192)
```

这是导出链路中明确存在的“归位”行为。

不过在 legacy osu! 格式和 stable 行为中，spinner 通常被视为固定在场地中心，文件中的 spinner 坐标不具有普通圆圈或滑条头相同的意义。

### B6. New Combo 规范化

解析时会强制：

- 第一个物件开启 New Combo。
- Spinner 后的第一个普通物件开启 New Combo。
- 只有实际开启 New Combo 时才保留 ComboOffset。

`GetPlayableBeatmap()` 中的 `OsuBeatmapProcessor.PreProcess()` 也会再次保证这项规则。

### B7. 滑条 repeat 限制

- 文件中的 legacy span count 会减 1，转换成 lazer 的 RepeatCount。
- RepeatCount 最低为 0。
- legacy span count 超过 9000 时直接抛出格式异常。

### B8. 零长度滑条 repeat 修复

如果计算出的滑条路径长度接近 0：

- RepeatCount 被强制设为 0。
- NodeSamples 只保留首尾。

这是为了避免已知的零长度滑条 repeat 异常及潜在 combo exploit。

### B9. 滑条期望长度限制

读取 legacy slider length 时：

- 长度最低为 0。
- 长度等于 0 时改为 `null`，由路径计算实际长度。

### B10. 坐标绝对值解析上限

物件坐标和滑条控制点坐标的绝对值上限为：

```text
131072
```

这不是标准游戏场边界。

因此：

- `X = -500`、`X = 1000` 等场外坐标可以正常解析。
- 绝对值超过 `131072` 会导致解析失败，而不是被钳制回游戏场。

## 6. `GetPlayableBeatmap()` 产生的变化

导出器会把解码结果转换为 ruleset 对应的 playable beatmap。

主要步骤：

1. Clone 原 beatmap。
2. 创建 ruleset converter。
3. 转换所有 hit object。
4. 执行 ruleset beatmap processor。
5. 对物件调用 `ApplyDefaults()`。
6. 执行 processor 后处理。

对于 osu! ruleset：

- HitCircle 位置直接复制。
- Slider 头位置和路径直接复制。
- 不存在游戏场边界钳制。
- Spinner 使用解码阶段已经生成的中心坐标。
- 物件会按时间排序。
- 会计算 slider duration、nested objects、stack height 等运行时派生数据。
- `OsuBeatmapProcessor.PreProcess()` 会规范化 New Combo。
- `PostProcess()` 会重新计算 stacking。

Stacking 的计算主要更新 `StackHeight`，不会把原始 hit object 的逻辑 Position 移回游戏场。

## 7. 重新编码造成的格式变化

`LegacyBeatmapEncoder` 会重新生成整个 `.osu` 文件，而不是修改原文本。

### C1. 文件版本统一

文件头统一写为：

```text
osu file format v128
```

原始格式版本不会保留。

### C2. Section 和字段顺序统一

固定输出：

1. `[General]`
2. `[Editor]`
3. `[Metadata]`
4. `[Difficulty]`
5. `[Events]`
6. `[TimingPoints]`
7. `[Colours]`
8. `[HitObjects]`

原文件中的以下内容不会原样保留：

- 空行数量
- 注释
- 字段顺序
- section 顺序
- 数字的原始文本格式

### C3. 未支持字段可能丢失

encoder 只写它明确支持的字段。

代码中明确未启用输出的字段包括：

- `UseSkinSprites`
- `AlwaysShowPlayfield`
- `OverlayPosition`
- `SkinPreference`

其他未被 decoder 保存、或未被 encoder 输出的字段同样可能丢失。

### C4. AudioFilename 路径规范化

`AudioFilename` 使用：

```csharp
Path.GetFileName(...)
```

如果原始值包含子目录，只保留文件名。

### C5. Metadata 条件输出

部分字段仅在满足条件时输出：

- Unicode 标题、艺术家为空时不输出。
- Source、Tags 为空时不输出。
- BeatmapID、BeatmapSetID 只有大于 0 时输出。

### C6. TimingPoints 重建

encoder 会：

- 深拷贝控制点。
- 从物件 SV 和 hitsample 信息中提取额外控制点。
- 按时间排序。
- 合并同一时间的控制点属性。
- 移除与上一个状态完全冗余的控制点。
- 将 lazer 控制点模型重新表示为 legacy 红线/绿线。

因此导出后：

- TimingPoints 行数可能改变。
- 行顺序可能改变。
- 等价属性可能被合并。
- 物件局部属性可能变成绿线。

### C7. Events 重建

encoder 先输出：

1. 背景事件
2. Break 事件
3. `UnhandledEventLines`

Storyboard 等无法完整解析的事件行通常会保存在 `UnhandledEventLines` 中，但它们相对于背景和 break 的位置可能改变。

### C8. Combo Colours 量化

Combo colour：

- 最多输出 decoder 支持的颜色数量。
- RGBA 浮点分量乘以 255 后转换为 byte。

因此小数颜色精度会丢失。

### C9. osu! 和 catch 物件坐标输出

对于 osu! 和 catch：

```csharp
position = ((IHasPosition)hitObject).Position;
```

随后直接写入 X/Y。

这里没有游戏场边界钳制。

### C10. mania 坐标重建

mania 的 X 坐标根据列数重新计算，不保留原始 X：

```text
floor((column + 0.5) * (512 / totalColumns))
```

### C11. 滑条长度输出

滑条长度优先使用：

```csharp
ExpectedDistance
```

如果为空则输出计算得到的 `Path.Distance`。

### C12. Hitsample 表达方式重建

encoder 会把 lazer hitsample 模型转换为 legacy：

- hit sound flags
- normal/addition sample bank
- custom sample index
- volume
- sample filename
- slider node samples

对于非 mania：

- 物件本地 custom sample bank 被写为 0。
- 物件本地 volume 被写为 0。
- 实际设置主要通过 TimingPoints 表达。

因此效果通常保持，但文本表达不一定与原文件相同。

### C13. 换行与编码统一

- 文本使用 UTF-8。
- 换行统一为 Windows CRLF。

## 8. 与场外物件直接相关的结论

### 普通圆圈

- 解码时接受场外坐标。
- 坐标绝对值不得超过 `131072`。
- playable conversion 直接复制坐标。
- `MutateBeatmap()` 只四舍五入。
- encoder 直接写出坐标。
- 不会被 lazer 导出器移动回游戏场。

### 滑条头

行为与普通圆圈相同：

- 不进行 `0-512 x 0-384` 钳制。
- 仅进行整数四舍五入。

### 滑条控制点

- 支持场外控制点。
- 控制点坐标会四舍五入。
- 多段/特殊路径可能转换为 Bezier。
- 不会因为超出标准游戏场而自动归位。

### Spinner

- legacy 解码器无条件放置在 `(256, 192)`。
- 这是唯一明确存在的场地中心归位。

### 极端坐标

- 坐标绝对值超过 `131072` 会导致解析失败。
- 这是防止异常数值的解析上限，不是标准游戏场限制。

## 9. stable 端问题的判断

如果导出的 `.osu` 中已经包含类似：

```text
-100,200,...
600,200,...
256,-100,...
256,500,...
```

但 stable 中表现为：

- 物件被移回场内；
- 编辑后坐标发生改变；
- 保存后坐标被规范化；
- 场外物件不可见或不可选；

则问题应归因于 stable 的：

- `.osu` 载入规则；
- 编辑器操作限制；
- 游戏场渲染或输入遮罩；
- 保存时的合法性修复；
- 对非标准谱面坐标的历史假设。

验证时应直接解压 `.osz` 并查看其中 `[HitObjects]` 的 X/Y，而不能只依据 stable 中显示出来的位置判断 lazer 是否修改了坐标。

## 10. 推荐的排查方法

以后调查导出差异时，建议按以下步骤：

1. 在 lazer 中保存谱面。
2. 找到 lazer 内部保存的原始 `.osu`。
3. 执行 `For compatibility (.osz)`。
4. 解压 `.osz`。
5. 比较两个 `.osu` 的语义内容。
6. 重点比较 `[HitObjects]`、`[TimingPoints]` 和 `[Difficulty]`。
7. 在导入 stable 前记录导出文件中的实际坐标。
8. 在 stable 打开后再次保存，并比较 stable 保存前后的 `.osu`。

可将问题分为三段：

```text
lazer 保存内容
    -> lazer compatibility exporter
    -> stable 载入和保存
```

只有先确定坐标在哪一段发生变化，才能准确选择修改位置。

## 11. 若未来需要减少导出转换

较容易独立取消、且通常不影响 stable 解析的项目：

- A1：GridSize 映射。
- A5：Break 时间取整。
- B1：难度参数范围限制，但 stable 可能自行限制。
- B2：Editor 参数范围限制。
- B5：Spinner 归位，但 stable 可能忽略 spinner 坐标。
- B10：提高坐标绝对值解析上限。

不建议轻易取消：

- A10：清除滑条末尾类型。
- A11：多段和特殊滑条转换为 Bezier。
- A12：使用重复控制点表示 stable Bezier 分段。
- TimingPoints 的 legacy 表达转换。
- Hitsample 到 legacy control points 的转换。

这些处理直接关系到 stable 是否能正确解析滑条、SV 和采样设置。

## 12. 当前处理决定

本次调查后决定：

- 不修改 `LegacyBeatmapExporter`。
- 不修改 `LegacyBeatmapDecoder`。
- 不修改 `LegacyBeatmapEncoder`。
- 保留原版 compatibility export 行为。
- 将场外物件在 stable 中的异常表现视为 stable 端兼容问题。
